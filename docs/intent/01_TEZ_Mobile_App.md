# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Мобильное приложение "Контроль присутствия" (Android)

**Версия документа:** 1.0
**Дата:** 04.11.2026
**Платформа:** Android (Native, Kotlin)
**Минимальная версия Android:** 8.0 (API 26)

---

## 1. ОБЩИЕ СВЕДЕНИЯ

### 1.1. Назначение системы
Мобильное приложение предназначено для сотрудников подрядчика и выполняет функции:
- Идентификации сотрудника на рабочем месте
- Сбора данных о присутствии в зонах действия BLE-маяков
- Передачи собранных данных на центральный сервер
- Защиты от фрода (передача аккаунта, использование чужого устройства)

### 1.2. Целевая аудитория
- **Сотрудник** — единственный пользователь мобильного приложения.
- Интерфейс максимально упрощён: приложение работает в фоновом режиме, не отвлекая от рабочих задач.

### 1.3. Стек технологий
| Компонент | Технология |
|-----------|------------|
| Язык | Kotlin |
| UI | Jetpack Compose (или XML, на выбор разработчика) |
| Локальная БД | Room (SQLite) |
| BLE-сканирование | Android BLE API + AltBeacon Library (рекомендуется) |
| Фоновая работа | Foreground Service + WorkManager |
| Сетевое взаимодействие | Retrofit2 + OkHttp |
| Биометрия | AndroidX Biometric |
| Архитектура | MVVM + Clean Architecture |

## 2. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 2.1. Авторизация и вход

#### 2.1.1. Первичный вход
- Пользователь вводит **логин** и **пароль**, полученные от администратора.
- После успешной проверки на сервере приложение:
  - Сохраняет JWT-токен доступа (access_token) и токен обновления (refresh_token) в защищённое хранилище (EncryptedSharedPreferences).
  - Запрашивает у пользователя установку **PIN-кода** (4-6 цифр) для быстрого входа.
  - Предлагает включить **биометрическую аутентификацию** (отпечаток / Face Unlock).

#### 2.1.2. Последующие входы
При повторном запуске приложения доступны три метода входа (в порядке приоритета):
1. **Биометрия** (если включена пользователем).
2. **PIN-код** (если установлен).
3. **Логин + пароль** (резервный вариант).

#### 2.1.3. Сессия
- Access_token имеет срок жизни 15 минут.
- Refresh_token — 30 дней.
- При истечении refresh_token требуется повторный вход по логину/паролю.
- Реализовать механизм **logout по команде с сервера** (push-уведомление).

### 2.2. Сбор данных с BLE-маяков

#### 2.2.1. Сканирование
- Приложение непрерывно сканирует BLE-окружение в фоновом режиме.
- **Основные пакеты:** фильтрует пакеты формата **iBeacon** с UUID из "белого списка" (получается с сервера при синхронизации).
- **Дополнительные пакеты (телеметрия маяков):**
  - **Eddystone-TLM** — пакеты с зарядом батареи, температурой, временем работы.
  - **Custom Manufacturer Data** с Company ID `0xFFFF` — пакеты с зарядом батареи и версией прошивки (для маяков без Eddystone-TLM).
- Частота сканирования: непрерывно, с интервалом отчётов 1 секунда.
- **Передача MAC-адреса:** для каждого обнаруженного маяка приложение сохраняет BLE MAC-адрес и отправляет его на сервер вместе с UUID для защиты от клонирования.

#### 2.2.2. Агрегация данных
Для каждого обнаруженного маяка приложение накапливает данные в течение **интервала агрегации** (по умолчанию 10 минут, настраивается с сервера):
- `beacon_uuid` — UUID маяка
- `major`, `minor` — идентификаторы маяка
- `mac_address` — BLE MAC-адрес маяка (для защиты от клонирования)
- `scan_timestamp_start` — время первого обнаружения в интервале
- `scan_timestamp_end` — время последнего обнаружения
- `median_rssi` — медианное значение RSSI за интервал
- `max_rssi`, `min_rssi` — экстремумы
- `samples_count` — количество замеров

**Агрегация телеметрии маяков (отдельный поток):**
- `beacon_uuid` — UUID маяка
- `mac_address` — MAC-адрес
- `battery_level` — заряд батареи (0-100%)
- `firmware_version` — версия прошивки
- `temperature` — температура маяка (если доступно)
- `last_seen_at` — время последнего получения телеметрии

#### 2.2.3. Хранение офлайн
- Все агрегированные пакеты сохраняются в локальную БД (Room).
- Каждый пакет имеет статус: `pending`, `synced`, `failed`.
- При отсутствии сети пакеты накапливаются неограниченно (с ротацией старых при достижении лимита 10 000 записей).

### 2.3. Синхронизация с сервером

#### 2.3.1. Автоматическая синхронизация
- Период отправки: настраивается с сервера (по умолчанию 10 минут).
- Условия отправки:
  - Наличие несинхронизированных пакетов в локальной БД.
  - Доступность сети (проверка через ConnectivityManager).
  - Наличие валидного access_token.

#### 2.3.2. Ручная синхронизация
- Пользователь может нажать кнопку "Синхронизировать" в главном экране.
- При отсутствии сети — показать сообщение "Нет соединения, данные сохранены локально".

#### 2.3.3. Обработка ошибок
- При ошибке 401 — попытка обновить access_token через refresh_token.
- При ошибке 403 — принудительный logout с уведомлением.
- При сетевых ошибках — экспоненциальная задержка повторных попыток (backoff).

#### 2.3.4. Защита от replay-атак
- Каждый запрос `POST /api/mobile/attendance` содержит уникальный `request_id` (UUID).
- Сервер проверяет уникальность `request_id` (хранит последние 1000 в Redis с TTL 24 часа).
- При обнаружении дубликата — отклонение запроса с кодом 409 Conflict.

#### 2.3.5. Валидация timestamps
- Все timestamps формируются в UTC через `System.currentTimeMillis()`.
- Приложение синхронизирует время с сервером при каждом входе (использует HTTP `Date` header или NTP).
- При обнаружении расхождения > 5 минут — предупреждение пользователю и отправка события `clock_skew_detected` на сервер.

### 2.4. Фрод-контроль на стороне клиента

#### 2.4.1. Fingerprint устройства
При первом входе приложение формирует усиленный отпечаток устройства:
```
fingerprint = SHA-256(
    Android_ID +
    Build.MANUFACTURER +
    Build.MODEL +
    Build.HARDWARE +
    Build.BOARD +
    Build.SERIAL (если доступен, API 26+) +
    TelephonyManager.getDeviceId() (если доступно)
)
```

**Дополнительно:**
- **Play Integrity API** (обязательно): получить аппаратно-привязанный токен `integrity_token` через `requestIntegrityToken()`. Проверить `deviceRecognitionVerdict` на `MEETS_DEVICE_INTEGRITY` и `MEETS_BASIC_INTEGRITY`.
- **MAC-адрес BLE-контроллера**: добавить в fingerprint (уникален для устройства).
- Отпечаток отправляется на сервер при каждом входе и с каждым пакетом attendance.
- При несовпадении отпечатка с сохранённым на сервере — блокировка сессии и уведомление администратора.

**Обработка смены устройства:**
- При первом входе — сохранить fingerprint.
- При несовпадении — создать `fraud_log` с типом `device_mismatch`, отправить на сервер.
- Сервер принимает решение: заблокировать или подтвердить смену (через push-уведомление).

#### 2.4.2. Защита от подмены
- **Root detection** (обязательно): проверка наличия `su` binary, Magisk, SuperSU. При обнаружении — отправка события `root_detected` на сервер (не блокировка, а информирование).
- Запрет работы на устройствах с включённым режимом разработчика (опционально, настраивается с сервера).
- **Запрет работы на эмуляторах** (обязательно): проверка через `Build.FINGERPRINT`, `Build.HARDWARE`, `Build.MODEL`, `Build.MANUFACTURER`. Проверка наличия telephony API (эмуляторы часто не имеют).
- **Play Integrity API** (обязательно): проверка `deviceRecognitionVerdict`. При отсутствии `MEETS_DEVICE_INTEGRITY` — отправка флага `untrusted_device` на сервер.
- **Mock BLE detection** (обязательно): проверка `isFromMockProvider()` для BLE-сканирования. При обнаружении mock-устройств — отправка события `mock_location_detected` на сервер.
- **Certificate Pinning** (обязательно): реализовать через OkHttp `NetworkInterceptor` с pins для конкретного CA или сертификата сервера. Обновление pins — через конфигурацию с сервера.

### 2.5. Получение настроек с сервера
При каждом входе и периодически (раз в час) приложение запрашивает:
- Список "белых" UUID маяков (для фильтрации сканирования).
- Интервал агрегации данных.
- Интервал синхронизации.
- Флаги безопасности (требования к fingerprint, запрет эмуляторов).

## 3. ПОЛЬЗОВАТЕЛЬСКИЙ ИНТЕРФЕЙС

### 3.1. Экран входа
- Поля: логин, пароль.
- Кнопка "Войти".
- Ссылка "Забыли пароль?" (отправка запроса на сброс через администратора).

### 3.2. Экран настройки безопасности (после первого входа)
- Ввод PIN-кода (4-6 цифр) + подтверждение.
- Переключатель "Использовать биометрию".
- Кнопка "Пропустить" (не рекомендуется).
- **Валидация PIN:** блокировка на 30 секунд после 5 неудачных попыток; возможность сбросить PIN через ввод логина/пароля.

### 3.3. Главный экран (рабочий)
**Минималистичный интерфейс:**
- **Статус работы:** "Сбор данных активен" / "Остановлено" / "Bluetooth выключен" (большой индикатор).
- **Состояние "Bluetooth выключен":** показать кнопку "Включить Bluetooth" с инструкцией.
- **Счётчик несинхронизированных пакетов.**
- **Время последней успешной синхронизации.**
- **Индикатор первой синхронизации:** "Сбор данных: идёт первый интервал агрегации (~X мин до первой отправки)".
- Кнопка "Синхронизировать сейчас".
- **Предупреждение о низком заряде батареи устройства** (< 15%): показать уведомление "Низкий заряд батареи — возможно прекращение сбора данных".
- Кнопка меню (⋮): Настройки, Выйти.

### 3.4. Экран настроек
- Смена PIN-кода.
- Включение/выключение биометрии.
- Информация о версии приложения.
- Политика конфиденциальности.

### 3.5. Уведомления (Foreground Service)
- Постоянное уведомление в шторке: "Контроль присутствия: сбор данных активен".
- При отсутствии сети — дополнительное уведомление: "Нет соединения, данные сохраняются локально".
- При низком заряде батареи устройства (< 15%) — уведомление: "Низкий заряд батареи — возможно прекращение сбора данных".

### 3.6. Управление разрешениями
**Пошаговый флоу запроса разрешений:**
1. При первом запуске — запрос `ACCESS_FINE_LOCATION` с объяснением: "Необходимо для сканирования BLE-маяков".
2. При отказе — показать экран-инструкцию с кнопкой "Открыть настройки" для ручного включения.
3. Для Android 13+ — запрос `POST_NOTIFICATIONS` с объяснением: "Для получения уведомлений о статусе сбора данных".
4. Проверка состояния разрешений перед каждым BLE-сканированием.

## 4. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

### 4.1. Производительность
- Потребление RAM: не более 100 МБ в фоновом режиме.
- **Потребление батареи: не более 10-15% в сутки** при активном использовании (пересмотрено с 3-5% из-за непрерывного BLE-сканирования).
- **Стратегия экономии батареи:**
  - **Scan duty cycle:** 3 секунды сканирование / 7 секунд пауза (или настраивается с сервера).
  - Использование `ScanSettings.SCAN_MODE_LOW_POWER` в паузах.
  - При отсутствии обнаруженных маяков за последние 5 минут — переход на интервал сканирования 10 секунд.
- Время холодного старта: не более 3 секунд.

### 4.2. Надёжность
- Приложение должно автоматически перезапускаться после перезагрузки устройства (Boot Completed Receiver).
- При падении процесса — автоматическое восстановление состояния из Room БД.
- **Self-watchdog:** приложение проверяет работоспособность Foreground Service каждые 5 минут. При обнаружении остановки — автоматический перезапуск service.
- **Проверка разрешений:** перед каждым BLE-сканированием проверка наличия необходимых разрешений (location, bluetooth). При отсутствии — повторный запрос или уведомление пользователя.
- Гарантия доставки данных: ни один агрегированный пакет не должен быть потерян при штатной работе.
- **Сохранение промежуточных данных:** каждые 2 минуты агрегации — сохранение промежуточных замеров RSSI в Room (для восстановления при краше процесса).

### 4.3. Безопасность
- Весь трафик — только по HTTPS (TLS 1.2+).
- Хранение токенов — в EncryptedSharedPreferences.
- Запрет на создание скриншотов приложения (FLAG_SECURE) — опционально.
- Логирование — только в debug-сборке, без персональных данных.

### 4.4. Совместимость
- Поддержка экранов от 4.7" до 7" (телефоны, небольшие планшеты).
- Поддержка темной и светлой темы (системная).
- Локализация: русский (основной), английский (опционально).

### 4.5. Доступность (Accessibility)
- **Поддержка TalkBack:** все интерактивные элементы имеют `contentDescription`.
- **Масштабирование шрифтов:** поддержка системного масштабирования шрифтов (до 1.5x).
- **Минимальный размер шрифта:** 12sp для текста, 14sp для основного контента.
- **Контрастность:** минимальное соотношение контраста 4.5:1 для текста (WCAG AA).
- **Touch targets:** минимальный размер интерактивных элементов 48x48dp.
- **Цветовая индикация:** не полагаться только на цвет (добавлять иконки или текст).

## 6. АЛГОРИТМЫ

### 6.1. Алгоритм агрегации RSSI
```
Для каждого интервала агрегации (10 минут):
  1. Собрать все замеры RSSI для конкретного маяка (ключ агрегации: beacon_uuid + major + minor).
  2. Отбросить крайние 10% значений (фильтр выбросов).
  3. Вычислить медиану оставшихся значений.
  4. Сформировать пакет с median_rssi, min, max, count, mac_address.
```

### 6.2. Алгоритм определения "присутствия"
- Если в течение интервала агрегации получено **≥ 3 замеров**, распределённых по всему интервалу (минимум 1 замер в каждой четверти интервала), с RSSI > порога (получается с сервера) → считать интервал "присутствием".
- Иначе — "прохождение мимо" (не учитывается).
- **Минимальная суммарная длительность:** сумма временных интервалов между замерами должна быть ≥ 30 секунд (для исключения случайных одиночных срабатываний).

### 6.3. Алгоритм ротации локальной БД
```
Если количество записей со статусом 'pending' > 10000:
  1. Пометить самые старые 1000 записей как 'expired'.
  2. Зафиксировать событие в локальном логе.
  3. Продолжить работу.
```

## 7. ОГРАНИЧЕНИЯ И ДОПУЩЕНИЯ

1. Приложение работает **только** при включённом Bluetooth.
2. На устройствах Android 6-11 требуется включённая геолокация (системное ограничение).
3. Производитель устройства обязан предупредить сотрудника о необходимости отключить "Оптимизацию батареи" для приложения.
4. Приложение не определяет координаты GPS — только факт нахождения в зоне BLE-маяка.
5. **Часовые пояса:** все timestamps формируются в UTC. Сервер обрабатывает и хранит в UTC. При отображении — конвертация в локальный часовой пояс пользователя.
6. **Обработка деактивированных маяков:** если маяк деактивирован на сервере (не входит в whitelist), приложение игнорирует его данные.

## 9. МАССОВОЕ РАЗВЁРТЫВАНИЕ

### 9.1. Стратегия назначения UUID
- **Рекомендуемый вариант:** единый UUID для всех маяков системы, различие по `major` (ID объекта/этажа) и `minor` (ID помещения/зоны).
- **Альтернатива:** уникальный UUID на каждый маяк (сложнее управление, но выше безопасность).

### 9.2. Whitelist UUID
- При первом запуске — запрос настроек перед началом сканирования.
- Кэширование whitelist в Room для офлайн-режима.
- При отсутствии сети — использование последнего закэшированного списка.
- Размер whitelist: до 1000 UUID (производительность фильтрации проверяется при тестировании).

### 9.3. Мониторинг состояния маяков
- Приложение отправляет список обнаруженных маяков (не только агрегированные данные присутствия) каждые 5 минут.
- Сервер отслеживает `last_seen_at` для каждого маяка. При отсутствии данных > 24 часов — пометка маяка как "неисправен" и алерт администратору.
