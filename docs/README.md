# Документация проекта "Контроль присутствия"

## Структура папок

```
docs/
├── intent/          # Технические задания (ЧТО разрабатываем)
├── spec/            # Спецификации и API (КАК устроено)
├── design/          # UI/UX требования (КАК выглядит)
├── qa/              # Критерии приёмки и тест-кейсы (КАК проверяем)
└── README.md        # Этот файл
```

---

## Назначение папок

### 📁 intent/ — Технические задания
**Для кого:** Продукт-менеджер, заказчик, разработчик (для понимания контекста)

**Что хранится:**
- ТЗ на разработку фичей и модулей
- Описание бизнес-требований
- Пользовательские сценарии
- Критерии приёмки

**Документы:**
- `01_TEZ_Mobile_App.md` — Мобильное приложение Android (авторизация, BLE, синхронизация)
- `02_TEZ_Beacon.md` — BLE-маяк (протокол iBeacon, варианты реализации)
- `03_TEZ_Server_Web.md` — Серверная часть и Web-интерфейс администратора

---

### 📁 spec/ — Спецификации
**Для кого:** Разработчик, архитектор, тестировщик

**Что хранится:**
- API-спецификации (OpenAPI/Swagger)
- Схема базы данных
- Описание протоколов и форматов данных
- Алгоритмы и бизнес-логика
- Технические требования к интеграциям

**Примеры документов (создавать по мере разработки):**
- `api-spec.md` — REST API эндпоинты, параметры, коды ответов
- `database-schema.md` — ER-диаграмма, описание таблиц
- `ble-protocol.md` — Спецификация BLE-пакетов и агрегации данных
- `auth-flow.md` — Спецификация аутентификации (JWT, refresh, fingerprint)

---

### 📁 design/ — UI/UX требования
**Для кого:** Дизайнер, frontend-разработчик, QA

**Что хранится:**
- Макеты экранов (mockups)
- Дизайн-система (цвета, типографика, отступы)
- Компоненты UI
- UX-сценарии и user flows
- Требования к адаптивности

**Примеры документов (создавать по мере разработки):**
- `design-system.md` — Цветовая палитра, шрифты, иконки
- `mobile-screens.md` — Макеты экранов мобильного приложения
- `web-ui-kit.md` — Компоненты Web-интерфейса
- `user-flows.md` — Сценарии использования

---

### 📁 qa/ — Критерии приёмки и тест-кейсы
**Для кого:** QA-инженер, тестировщик, разработчик (при приёмке)

**Что хранится:**
- Критерии приёмки фич (acceptance criteria)
- Тест-кейсы (позитивные/негативные сценарии)
- Чек-листы для ручного тестирования
- Автоматизированные тест-сценарии
- Баг-репорты и шаблоны для них

**Примеры документов (создавать по мере разработки):**
- `mobile-app-acceptance.md` — Критерии приёмки мобильного приложения
- `api-test-cases.md` — Тест-кейсы для REST API
- `ble-integration-tests.md` — Тесты интеграции с BLE-маяками
- `security-checklist.md` — Чек-лист проверок безопасности

## Как пользоваться

### При разработке новой фичи:

1. **Понять контекст** → открыть `intent/` и прочитать соответствующее ТЗ
2. **Узнать детали реализации** → открыть `spec/` и найти спецификацию
3. **Реализовать UI** → открыть `design/` и следовать макетам
4. **Проверить результат** → открыть `qa/` и пройти тест-кейсы

### При создании документации:

1. **Новая фича?** → создай документ в `intent/` (формат: `XX_Название.md`)
2. **Нужна спецификация?** → создай документ в `spec/` (формат: `название-spec.md`)
3. **Новый UI компонент?** → создай документ в `design/` (формат: `название-ui.md`)
4. **Критерии приёмки?** → создай документ в `qa/` (формат: `название-acceptance.md` или `название-test-cases.md`)

### Соглашения:

- Нумерация в `intent/` — по порядку создания (`01_`, `02_`, ...)
- Имена файлов — на английском, lowercase, с дефисами (`api-spec.md`)
- Каждый документ должен иметь заголовок, версию и дату создания
- Связанные документы — ссылаться друг на друга через относительные пути

---

## Быстрый старт для разработчика

1. Прочитать ТЗ в `intent/` — понять **ЧТО** нужно сделать
2. Открыть спецификацию в `spec/` — понять **КАК** это реализовать
3. Свериться с `design/` — понять **КАК** это должно выглядеть
4. Реализовать → протестировать → задокументировать изменения
